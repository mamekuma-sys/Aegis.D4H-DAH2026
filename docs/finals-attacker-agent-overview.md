# 본선 공격 에이전트 한눈에 이해하기

이 문서는 코드를 처음 보는 팀원도 공격 에이전트의 역할과 실행 흐름을 설명할 수 있도록 만든 입문용 문서다. 상세 설계는 [`2026-08-11-attacker-runtime-design.md`](superpowers/specs/2026-08-11-attacker-runtime-design.md), 실제 코드는 [`agents/attacker`](../agents/attacker)에서 확인한다.

## 30초 설명

공격 에이전트는 운영진이 알려 준 상대 팀 주소와 포트를 하나씩 확인하고, **실제로 관측한 인터페이스에만** 검증된 공격을 시도한다. 응답에서 `FLAG{...}`를 찾으면 중복을 제거해 제출 서버로 전송한다. 이미 성공한 공격 방법은 같은 구조의 다른 서비스에 재사용하고, 결정론적 방법으로 풀리지 않을 때만 LLM의 조언을 제한적으로 사용한다.

한 문장으로 줄이면 다음과 같다.

> **관측 → 증거에 맞는 계획 → 제한된 실행 → 플래그 제출**을 반복하는 공격 자동화 프로그램이다.

## 쉬운 비유

처음 방문한 건물에서 보물을 찾는 조사팀이라고 생각하면 쉽다.

1. 운영진이 준 건물 목록만 방문한다.
2. 먼저 현관과 안내문을 살펴 실제 출입구와 시설을 파악한다.
3. 관측한 출입구에 맞는 검증된 열쇠부터 사용한다.
4. 열쇠가 맞아 플래그를 찾으면 즉시 제출한다.
5. 같은 구조의 다른 건물에는 성공한 열쇠를 재사용한다.
6. 기존 열쇠가 모두 실패했을 때만 LLM에게 다음 후보를 묻는다.

중요한 점은 **보이지 않은 문을 상상해서 무작정 두드리지 않는 것**이다.

## 입력과 출력

| 구분 | 내용 | 초보자용 설명 |
|---|---|---|
| 입력 | `TARGETS` | 공격이 허용된 상대 팀 주소 목록 |
| 입력 | `PORTS` | 운영진이 공개한 진입 포트 목록 |
| 입력 | `SUBMIT_URL`, `SUBMIT_TOKEN` | 찾은 플래그를 점수로 바꾸기 위한 제출 정보 |
| 선택 입력 | `LLM_BASE_URL`, `LLM_API_KEY` | 결정론적 공격이 실패할 때 받을 보조 조언 |
| 출력 | 공격 요청 | 허용된 `TARGETS × PORTS` 범위 안의 요청 |
| 출력 | 플래그 제출 | 찾은 플래그를 제출 서버에 전송 |
| 출력 | 구조화 로그·라운드 요약 | 비밀 원문을 제외한 요청 수, 제출 결과, LLM 사용량 |

주소, 토큰, 키는 이미지에 넣지 않고 본선 환경변수로만 주입한다.

## 전체 실행 흐름

```text
운영진 환경변수
      │
      ▼
TARGETS × PORTS 전체 열거
      │
      ▼
HTTP → 필요 시 HTTPS → 필요 시 수동적 TCP 배너 관측
      │
      ▼
관측 증거와 서비스 특징 생성
      │
      ├─ 알려진 L1~L3 공격과 관측 기반 공격 실행
      ├─ 이전 성공 playbook 재사용
      └─ 그래도 실패하면 제한된 LLM 조언 사용
      │
      ▼
응답 본문·헤더에서 FLAG 추출
      │
      ▼
중복 제거 → 제출 → 결과 기록
```

### 1. 라운드 준비

런타임은 라운드마다 요청 예산, 증거, 성공 playbook, 플래그 중복 집합, 비밀 저장소를 새로 만든다. 제출 토큰과 LLM 키는 일반 문자열처럼 컴포넌트 사이를 돌아다니지 않고 라운드 한정 비밀 저장소의 불투명한 handle로 전달된다. 라운드가 끝나면 이 임시 상태를 폐기한다.

### 2. 모든 표적을 공정하게 순회

공격 범위는 운영진이 준 `TARGETS × PORTS`의 모든 조합이다. 기본 8개, 최대 32개의 worker가 병렬로 처리하지만 초당 요청 제한과 제출 제한은 전체가 공유한다. 알려진 데모 포트가 함께 들어오면 새 레이어인 L4를 일찍 확인하면서도 L1~L3를 같은 wave에 유지한다.

### 3. 프로토콜을 먼저 관측

각 endpoint에서 먼저 평문 HTTP `GET /`을 보낸다. 응답이 없을 때만 HTTPS로 다시 확인하고, 그것도 응답이 없을 때만 TCP 배너를 읽는다. TCP 배너 단계는 최대 4KiB, 750ms이며 애플리케이션 데이터를 보내지 않는다.

이 순서 덕분에 `PORTS`에 HTTP가 아닌 서비스가 포함돼도 HTTP라고 단정하지 않는다. 대상 서비스의 self-signed 인증서는 공격 대상 연결에서만 허용하며 제출 서버와 LLM 연결의 인증서 검증은 완화하지 않는다.

### 4. 관측 증거에 묶어 공격

관측 결과에는 endpoint, 라운드, 만료 시간이 포함된 evidence가 붙는다. 공격 계획은 실행 직전에 다음을 다시 확인한다.

- 현재 라운드의 계획인지
- 방금 관측한 같은 endpoint를 대상으로 하는지
- evidence와 계획이 만료되지 않았는지
- 허용된 공격 대상 범위인지
- 읽기 전용 작업인지

조건이 맞지 않으면 실행하지 않는다. 오래된 evidence라면 루트 경로를 한 번 다시 관측해 새 evidence에 결속한다.

### 5. 비용이 싼 공격부터 실행

LLM보다 먼저 코드로 정해 둔 결정론적 공격을 사용한다.

| 레이어 | 현재 관측으로 확인된 주요 형태 |
|---|---|
| L1 | 내부 helper 접근 SSRF, config 경로 traversal |
| L2 | 관리자 session 위조, loopback secret·registry SSRF |
| L3 | `app_meta` 대상 SQL injection, 직접 노출 route |
| L4 | 구체 인터페이스를 가정하지 않고 실제 응답이 공개한 route·parameter만 사용 |

미확인 서비스에서는 상태·문서용 GET만 제한적으로 보내며, 파괴적 action이나 traversal route를 임의로 실행하지 않는다. 응답이 전혀 없는 endpoint는 1초 뒤 다시 확인하고, 응답은 있었지만 성공하지 못한 endpoint는 기본 30초 cooldown을 둔다.

### 6. 성공 방법 재사용

플래그를 실제로 회수한 요청 형태는 playbook에 기록한다. 같은 구조 fingerprint를 가진 다른 상대 서비스에는 이 방법을 먼저 재사용한다. 한 서비스 구조를 여러 worker가 동시에 LLM으로 풀지 않도록 single-flight로 한 worker만 solver 역할을 맡는다.

### 7. 필요한 경우에만 LLM 사용

LLM은 공격을 직접 실행하지 않는다. 관측 내용을 바탕으로 다음 읽기 전용 요청 후보를 제안할 뿐이며, 런타임이 출력 형식과 관측된 인터페이스를 다시 검증한 뒤 실행한다.

- LLM 키가 없어도 알려진 공격과 관측 기반 공격은 정상 실행된다.
- 한 endpoint에서 최대 4 turn, 한 라운드에서 최대 48회만 호출한다.
- 관측 입력은 UTF-8 8KiB로 제한한다.
- 플래그, 제출 토큰, API 키를 prompt와 로그에 넣지 않는다.
- 모델의 제안이 관측되지 않은 route나 변경 작업을 요구하면 거부한다.

즉, 이 에이전트의 중심은 LLM이 아니라 **결정론적 런타임과 검증 경계**다.

### 8. 플래그 처리와 제출

모든 응답 본문과 일부 헤더에서 `FLAG{...}` 형태를 찾는다. 같은 플래그는 hash로 중복을 막고 `accepted`, `own_team`, `duplicate`, `rejected`, `closed`를 구분해 기록한다. 제출은 분당 30회로 제한하고 HTTP 429가 오면 backoff한다. 플래그 원문은 로그에 남기지 않는다.

## 주요 코드 지도

| 파일 | 역할 |
|---|---|
| `config.py` | 환경변수 파싱, `TARGETS × PORTS` 생성 |
| `observation.py` | HTTP·HTTPS·수동적 TCP 관측과 evidence 생성 |
| `profiles.py` | 서비스 구조 fingerprint와 취약점 힌트 생성 |
| `exploits.py` | 관측으로 확인된 결정론적 공격 후보 |
| `planner.py`, `llm_advisor.py` | 제한된 LLM 조언을 계획으로 변환 |
| `tools.py`, `egress.py` | 실행 직전 evidence·범위·부작용·네트워크 목적지 검증 |
| `playbook.py` | 성공한 요청 형태의 교차 표적 재사용 |
| `flags.py` | 플래그 추출, 중복 제거, 제출 상태 관리 |
| `secrets.py`, `audit.py` | 라운드 비밀 격리와 로그 비식별화 |
| `runtime.py` | 위 구성요소를 연결하는 전체 오케스트레이터 |
| `__main__.py` | 컨테이너 진입점 `python -m aegis_attacker` |

## 왜 이렇게 설계했나

- **관측 우선:** 예선 보고서에 있던 신호가 본선 패킷에 그대로 있다고 가정하지 않는다.
- **결정론 우선:** 빠르고 재현 가능하며 LLM 토큰을 아낀다.
- **증거 결속:** 오래되거나 다른 표적의 관측으로 잘못 공격하는 일을 막는다.
- **범위 제한:** 운영진이 허용한 상대 진입점, 제출 서버, 대회 LLM만 통신한다.
- **비밀 격리:** 플래그와 토큰이 prompt나 로그에 섞이는 것을 막는다.
- **장애 격리:** 한 endpoint의 오류가 다른 상대 공격을 중단시키지 않는다.

## 현재 한계와 당일 확인 사항

- L4는 구체 인터페이스가 관측되지 않아 경로를 하드코딩하지 않았다. 본선에서 실제 응답을 본 뒤 그 범위 안에서 적응한다.
- `TARGETS` 또는 `PORTS`가 없으면 안전하게 아무 공격도 하지 않는다.
- 제출 토큰이 없으면 플래그를 찾아도 점수로 제출할 수 없다.
- 최종 팀 번호, 제출 토큰, LLM 키는 현장에서 받은 값으로 주입하고 그때 이미지를 빌드·push한다.

## 자주 받을 질문과 답변

### “그냥 LLM에게 전부 맡긴 에이전트인가요?”

아니다. 확인된 공격, 범위 검증, rate limit, 플래그 제출은 모두 결정론적 코드다. LLM은 이 방법들이 실패했을 때 제한된 읽기 전용 후보만 제안한다.

### “처음 보는 L4도 공격할 수 있나요?”

정해지지 않은 경로를 추측해서 난사하지는 않는다. 루트·상태·문서 응답이 실제로 공개한 route와 parameter를 발견한 뒤 그 인터페이스 안에서만 적응한다.

### “상대 팀 주소를 코드에 넣어 뒀나요?”

아니다. 운영진이 주입한 `TARGETS`와 `PORTS`를 사용하며 모든 조합을 누락 없이 순회한다.

### “플래그나 토큰이 로그 또는 LLM으로 새지 않나요?”

라운드 비밀 저장소, redaction, prompt 크기·내용 검사로 분리한다. 로그에는 플래그 원문 대신 fingerprint와 제출 상태만 남긴다.

### “한 서비스가 죽어 있으면 전체가 멈추나요?”

아니다. endpoint별 오류를 격리하고 짧은 cooldown 뒤 다시 확인하므로 나머지 상대와 포트는 계속 처리한다.

## 발표할 때 그대로 말할 수 있는 설명

> 저희 공격 에이전트는 독립 Docker 이미지로 동작합니다. 운영진이 준 상대 주소와 포트 전체를 먼저 관측하고, 그 관측에서 발급한 evidence에 공격 계획을 묶어 실행합니다. 확인된 L1부터 L3 공격과 성공 playbook을 먼저 사용해서 빠르고 싸게 플래그를 찾고, 풀리지 않은 서비스만 제한적으로 LLM 조언을 받습니다. 찾은 플래그는 중복 제거 후 제출하며, 토큰과 플래그 원문은 로그나 LLM 입력에 남기지 않습니다. 아직 인터페이스를 모르는 L4는 경로를 하드코딩하지 않고 본선에서 실제로 보이는 인터페이스에만 적응하도록 만들었습니다.
